What DevX prepares

Three notes, written from the diff.

  1. 01

    Pull-request brief

    A short review of the change: the files that matter, the behavior that moved, and the question a reviewer should ask first.

  2. 02

    Answers from the repo

    Ask where a behavior lives. DevX points at files and functions in the repository you connected, instead of guessing from a snippet pasted into a blank chat.

  3. 03

    A record you can keep

    When the change merges, DevX drafts a changelog line and a doc edit so the explanation does not stay trapped in a chat thread.

Sample brief

Short enough to paste into the pull request.

This is the shape of the note DevX writes. It is a product preview, from a sample change, not a customer story.

billing-service

PR #482 · ready for review

Tax rounding moved into tax/calc.ts

What changed

Invoice tax is rounded in one function. The API handler calls it instead of rounding inline.

Look here first

  • tax/calc.ts — new roundTax()
  • api/invoice.ts — two call sites updated
  • tests/invoice.test.ts — zero-tax case still missing

Risk

European invoices that use half-up rounding may shift by one cent.

Suggested note

Please add a test for a zero-tax line before merge.

How access works

One repository to start.

DevX is in early access. We onboard a small number of teams and keep the first connection limited to a single repository.

  1. Grant read access

    GitHub or GitLab. Read access is enough for the first brief.

  2. Open a pull request, or ask

    DevX drafts the brief beside the change, or answers a question about the code.

  3. Keep what is useful

    You copy the note into the pull request or the changelog. DevX does not post it for you.
